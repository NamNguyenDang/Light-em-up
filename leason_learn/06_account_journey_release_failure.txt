FR-29: ACCOUNT JOURNEY WAS NOT USABLE ON THE LATEST DEFAULT BRANCH
Reported by user: 18 November 2026.
Status: release blocker; not fixed by this record.

WHAT THE USER EXPERIENCED
The user could not log in, register an account, or light a personal candle.

WHAT SOURCE INSPECTION CONFIRMED
The shipped public Supabase URL/key are empty. Sign-in intentionally becomes unavailable.
There is no account registration UI/flow. Optional Google is disabled.
The primary Add your candle action depends on verified authentication, so the unavailable
account journey blocks it too. The local saved-light demo does not satisfy online acceptance.
Live schema/provider/redirect setup was not verified. Do not invent a database diagnosis.

WHAT WE GOT WRONG
We described merged feature implementation more prominently than actual usable-release
status. SDK HTTP fixtures and PostgreSQL claim fixtures passed, but they did not exercise
registration or prove that the deployed default branch had effective backend configuration.
Previously noting missing configuration was accurate, but it was not a substitute for
tracking the core journey as blocked. A green accessibility/fixture run is insufficient.

RULE TO PREVENT REPEAT
Report implementation, deployment and end-to-end user acceptance as separate statuses.
A release must verify the served configuration and the real deployed-origin journey:
register -> confirm if required -> sign in -> create/light/save candle -> refresh ->
sign out/in -> confirm persisted ownership and lit state.
No mocked network routes in the live smoke suite. Missing config or skipped required
scenarios mean BLOCKED/NOT RUN, not PASS. Never fabricate account or candle success.
Keep fixture regressions for error branches and accessibility; they complement live tests.

REGRESSION AND CLOSURE RECORD
See docs/FR-29_ACCOUNT_JOURNEY_RELEASE_BLOCKER.md for FR29-01 through FR29-09.
Keep signup confirmation, password-manager/paste, keyboard/focus, errors, retry, persistence
and cross-account authorization in scope. Never weaken RLS or confirmation for a passing test.
FR-29 requires implementation plus real-service acceptance evidence before closure.
